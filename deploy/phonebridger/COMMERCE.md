Do not turn policy booleans into a substitute for evidence. Current code accepts fixed amounts with zero separately calculated tax; a real tax calculation requires a separately reviewed implementation. 2. Create/select a separate Stripe sandbox for PhoneBridger. Do not operate the selected live context with `livemode:false`. Keep sandbox IDs and keys distinct. If CLI creates an anonymous sandbox, claim it before using MCP. Never create test records in the live merchant account.
3. Supply an ignored restricted sandbox key with the documented Accounts read and Checkout Sessions write/read plus the minimum permissions Stripe requires for inline price/product creation. Prefer a RAK. Supply the webhook signing secret separately. Keys are `STRIPE_RESTRICTED_KEY` and `STRIPE_WEBHOOK_SECRET`, never browser code, command arguments, Git or chat. Copy protected files through Wrangler stdin using the existing secret-upload pattern; a secret deployment is itself a version change.
4. Register `/api/shop/webhook` for `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `checkout.session.expired`, `charge.refunded`, `charge.dispute.created`. Receive raw signed bytes. The correct account/mode, canonical Session amounts, expanded PaymentIntent and latest charge are checked. A refund/dispute that predates checkout completion cannot grant an entitlement. No fulfilment from the success page.
5. Apply `commerce-schema.sql` and additive `commerce-operations.sql` only to the dedicated database. Use confirmed physical stock for stocked orders, or the explicit manual_dropship model for supplier procurement. The latter records its immutable order model in commerce_procurement and never invents warehouse stock or consumes stocked-order inventory. No seeded stock or fictitious orders/reviews in production. Reservations are transaction guarded and survive delayed/ambiguous payment states. Definitive creation errors release stock; uncertain timeouts require reconciliation using the same order/idempotency key. Do not sweep all expired local reservations: an accepted asynchronous Stripe payment can still be pending.
6. Test hosted sandbox checkout, decline/cancel/delayed payment, duplicate and out-of-order events, stock contention, refund/dispute, paid digital delivery and physical dispatch with isolated synthetic data. Local SDK-signed tests are not a provider end-to-end result. Retain exact sandbox evidence privately.
7. Canonical paid Checkout automatically issues the storefront entitlement; app-only orders become fulfilled automatically. Hardware stays awaiting dispatch. The separately credentialed operator route records dispatch/tracking, consumes stock once and confirms delivery before review eligibility. Customer sessions cannot call it. `operator.mjs` reads protected credentials from a file. A typed reference is not proof of actual carrier delivery. Refunds revoke entitlement/review eligibility; returned dispatched goods require inspection before inventory is restocked. Partial refunds and resolved disputes require operator reconciliation; do not automatically restore a licence or resell returned inventory.
8. Purchasers use their private `/checkout?order=<id>` record to submit one real review after paid fulfilment. `moderateReview` records the reason in an audit table. Publish relevant critical reviews as well as positive ones. Rejection reasons concern spam/privacy/irrelevance/abuse/duplicates, never a low score. Public output excludes account email/address. Browser output uses text nodes to prevent review HTML injection.
9. Repeat the verified contract with a restricted live key and correct live webhook. Confirm the exact live account and charges_enabled; track payout verification separately and obey any actual Stripe charge restriction. Only then select live mode in the reviewed policy and deploy. Recheck actual canonical-domain routes, noindex/private order access, financial totals and the exact release version. No paid hosting upgrade is assumed.

## Tests and limits

`node --test tests/stripe-commerce.test.mjs` uses in-memory SQLite transactions and the actual pinned SDK's signature implementation. It covers policy gates, authoritative amounts, request idempotency, stock exhaustion, unsigned/stale/wrong-mode events, canonical unpaid/paid handling, owner-only orders, real-review qualification, moderation, refunds and idempotent fulfilment. Provider sandbox acceptance is recorded in [PLAYGROUND.md](PLAYGROUND.md). Actual payout readiness, legal/tax review, native activation and physical delivery remain separate launch checks. Live Session creation requests a Stripe payment receipt for the buyer email. This is not evidence of actual delivery until Stripe sends the paid receipt; no application purchase email or VAT invoice is certified. Purchasers can download private payment summaries and licence records; these do not replace tax invoices or native activation.

Retrieve current primary docs before extending the integration: [Checkout](https://docs.stripe.com/payments/accept-a-payment?payment-ui=checkout&ui=stripe-hosted), [fulfilment](https://docs.stripe.com/checkout/fulfillment), [webhooks](https://docs.stripe.com/webhooks), [restricted keys](https://docs.stripe.com/keys), [sandboxes](https://docs.stripe.com/sandboxes). A plugin skill's version table can lag the installed SDK; inspect its generated API types and API version before authoring parameters.
