# PhoneBridger commerce release contract

Owner selected **MB Memocasting**, 6 October 2026. Recommended Stripe implementation guide was retrieved and accepted before coding: hosted Checkout, one-time payment, no Connect/creator platform. Do not change the existing merchant's company details, other store settings or global branding to configure this separate product. Per-session PhoneBridger branding is supported by the pinned Stripe SDK **23.0.0**, API **2026-09-30.endive**. The SDK's current hosted default is used; outdated `ui_mode: 'hosted'` examples are not copied.

## Current release boundary

`commerce-policy.json` is deliberately disabled. It records proposed USD prices 29/49/65/79 and the selected seller/account, not a completed live tax/shipping/licence offer. Plugin OAuth permits supported MCP operations; it does not give the Worker an API key. No live Stripe product, price, checkout, charge, refund or payment-method setting was created during this preparation.

Live account read showed charges enabled but payouts disabled and outstanding owner verification. The owner must resolve the actual Dashboard requirements. Do not upload identity documents or invent owner records. Hardware stock, shipping origin/destinations/rates/times, package contents, tax treatment, purchase/return terms and final digital delivery remain open. The native beta remains freely downloadable and has no paid unlocking enforcement; an entitlement record is a storefront purchase record, not an implemented native activation system.

The shop is a working product/configuration/enquiry page while these facts are missing. Real paid order and review endpoints are implemented, tested locally, and fail closed. Real reviews start empty. No external-retailer reviews, AI testimonials or aggregate rating are manufactured. The homepage's separately labelled illustrations remain unchanged.

## Configuration and activation sequence

1. Finish seller, fulfilment, licence delivery, tax and return facts. Rewrite the public shop/privacy/terms against those facts and review the exact edition through Studio. Do not turn policy booleans into a substitute for evidence. Current code accepts fixed amounts with zero separately calculated tax; a real tax calculation requires a separately reviewed implementation. Do not enable `automatic_tax` without active registrations.
2. Create/select a separate Stripe sandbox for PhoneBridger. Do not operate the selected live context with `livemode:false`. Keep sandbox IDs and keys distinct. If CLI creates an anonymous sandbox, claim it before using MCP. Never create test records in the live merchant account.
3. Supply an ignored restricted sandbox key with the documented Accounts read and Checkout Sessions write/read plus the minimum permissions Stripe requires for inline price/product creation. Prefer a RAK. Supply the webhook signing secret separately. Keys are `STRIPE_RESTRICTED_KEY` and `STRIPE_WEBHOOK_SECRET`, never browser code, command arguments, Git or chat. Copy protected files through Wrangler stdin using the existing secret-upload pattern; a secret deployment is itself a version change.
4. Register `/api/shop/webhook` for `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `checkout.session.expired`, `charge.refunded`, `charge.dispute.created`. Receive raw signed bytes. The correct account/mode and canonical Session amounts are checked. No fulfilment from the success page.
5. Apply `commerce-schema.sql` only to the dedicated database. Add confirmed physical stock using the operator's actual inventory; no seeded stock or fictitious orders/reviews in production. Reservations are transaction guarded and survive delayed/ambiguous payment states. Definitive creation errors release stock; uncertain timeouts require reconciliation using the same order/idempotency key. Do not sweep all expired local reservations: an accepted asynchronous Stripe payment can still be pending.
6. Test hosted sandbox checkout, decline/cancel/delayed payment, duplicate and out-of-order events, stock contention, refund/dispute, paid digital delivery and physical dispatch with isolated synthetic data. Local SDK-signed tests are not a provider end-to-end result. Retain exact sandbox evidence privately.
7. Operator confirms actual digital delivery and dispatch before `fulfilOrder` records fulfilment. A delivery/reference string is not proof by itself. The helper issues one storefront entitlement and consumes stock once. No public admin mutation route exists; connect it only to an authenticated maintained operator tool. Refunds revoke entitlement/review eligibility; returned dispatched goods require inspection before inventory is restocked. Partial refunds and resolved disputes require operator reconciliation; do not automatically restore a licence or resell returned inventory.
8. Purchasers use their private `/checkout?order=<id>` record to submit one real review after paid fulfilment. `moderateReview` records the reason in an audit table. Publish relevant critical reviews as well as positive ones. Rejection reasons concern spam/privacy/irrelevance/abuse/duplicates, never a low score. Public output excludes account email/address. Browser output uses text nodes to prevent review HTML injection.
9. Repeat the verified contract with a restricted live key and correct live webhook. Confirm live account charges AND payouts/requirements. Only then select live mode in the reviewed policy and deploy. Recheck actual canonical-domain routes, noindex/private order access, financial totals and the exact release version. No paid hosting upgrade is assumed.

## Tests and limits

`node --test tests/stripe-commerce.test.mjs` uses in-memory SQLite transactions and the actual pinned SDK's signature implementation. It covers policy gates, authoritative amounts, request idempotency, stock exhaustion, unsigned/stale/wrong-mode events, canonical unpaid/paid handling, owner-only orders, real-review qualification, moderation, refunds and idempotent fulfilment. Provider sandbox, actual payout readiness, legal/tax review and delivery are separate pending checks. No customer email is sent by this preparatory service.

Retrieve current primary docs before extending the integration: [Checkout](https://docs.stripe.com/payments/accept-a-payment?payment-ui=checkout&ui=stripe-hosted), [fulfilment](https://docs.stripe.com/checkout/fulfillment), [webhooks](https://docs.stripe.com/webhooks), [restricted keys](https://docs.stripe.com/keys), [sandboxes](https://docs.stripe.com/sandboxes). A plugin skill's version table can lag the installed SDK; inspect its generated API types and API version before authoring parameters.
