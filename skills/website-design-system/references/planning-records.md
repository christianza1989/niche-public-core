# Planning records

Read when starting a full identity or planning multiple pages. Extend existing site documentation; do not create parallel databases or a mandatory document forest. A compact DESIGN plus linked page/asset records is often sufficient.

## Brief and route map

Record the active niche/site, audience and key uncertainties; confirmed offer/capabilities; language/locale; existing identity/assets; requested scope; current stage and meaningful next action. Keep evidence/date, hypothesis and unresolved dependency distinct. Competitor observations and generated concepts are not facts about our business.

For each authorized page, record:

| Field | Decision |
|---|---|
| Route and family | Actual route, public/editorial/shop/contact/auth/operational mode |
| User job | The question or task completed here |
| Entry/exit | Real source pages, navigation, primary CTA destination, return path |
| Content/data | Approved content, product or existing API source; isolated fixtures when explicitly prototyping |
| Capability | Present, to implement within scope, dependency, or deferred |
| Composition | Desktop/mobile content order, density, important states |
| Acceptance | Observable route-specific result and evidence |

Plan the complete requested journey before polishing its isolated screens. A site map is not permission to implement every future route. A homepage purchase CTA, product choice and its handoff must agree; if checkout is unavailable the destination and wording must describe the true present action. Authenticated areas need actual role/capability contracts or a clearly scoped private prototype.

## Durable art direction

Persist chosen concept/version/actor, reference decisions and the audience-specific visual thesis. Specify palette by semantic role; font sources, weights and locale glyph support; type/reading widths; grid, spacing, radii, borders, surfaces; logo and icon construction; image framing/lighting; responsive behavior and motion intent. Reuse current tokens/components before introducing alternatives.

Separate signature treatments from quiet functional surfaces. A visually expressive homepage does not require every form field, dashboard row or legal paragraph to use a glowing card. Judge consistency by identity and hierarchy, not by repeating one composition.

Use a whole-page sketch to check information density and rhythm before high-detail production. Pick a representative composition to calibrate the identity; do not demand generation of the entire long page at once. Mobile may reorder or replace a composition while retaining essential information and the same task.

## Section/interaction specifications

For every planned section or functional region specify purpose/user question, copy/data source, composition, asset roles/IDs, responsive order/crop, CTA/interaction, applicable states and dependencies. Record a no-image decision where text, a form, table or vector is the right representation.

Plan each junction jointly: outgoing and incoming background, light, spacing, contrast and reading continuity. Decide whether a continuous scene, quiet space, line or thematic change actually helps orientation. Keep the footer and header part of the journey, not late decorative additions.

For a stateful region specify where state comes from and what persists. Identify applicable default/focus/selected/loading/empty/error/success/disabled states, plus role access and recovery where relevant. Do not impose irrelevant states on static prose. An implementation task tests these states; a concept task records them as proposed.

## Asset inventory

Use the [asset-kit contract](../../webpage-section-asset-kit/references/asset-kit-contract.md). Include role/ID, reuse/edit/generate decision, representation, source and invariants, approximate displayed size/proportions, mobile focal area, alpha/shadow policy and semantic intent. Distinguish site-wide masters from one-page scenes. Inventory describes final use, not a quota of images.

Retain full-detail product masters and exact logos/screens separately from the concept. Check the planned set together for repeated empty atmosphere, inconsistent perspectives or an unnecessary new product rendering. Reuse one master for quantity arrangements; use a reviewed distinct master for a real variant or different required view.

## Progressive implementation

The plan is versioned working context. Update it when actual-browser findings improve the composition, when a real capability changes, or when the owner changes direction. Preserve selected originals and historical evidence; do not rewrite old reviews as if they used the new plan. Continue from existing progress after compaction or a new session.

Batching is allowed: shared icons, reviewed product variants and CSS components can be prepared together. Integrate and inspect a representative unit before bulk generation or repeating an error across routes. Full-page review happens periodically and before delivery, not only at the end of each independent asset.
