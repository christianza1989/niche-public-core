# Commerce acceptance

Use when the task includes real payment, orders or customer reviews. Preserve the selected brand and page-family design; these checks concern the actual service behind it. A working selection/enquiry page can ship while the paid route remains explicitly unavailable.

## Establish what can actually be sold

Record seller/provider account, currency, price basis, licence/service delivery, physical stock, supported destinations, shipping and return/tax treatment from confirmed facts. Delegate routine choices only within the user's scope. Supplier cost or a retailer reference does not establish inventory, included accessories, fulfilment dates, our return terms or our customer rating. A physical software-box illustration needs a digital-delivery explanation when no box ships.

Inspect the connected account before mutating it. Payment permission, payout readiness and outstanding provider requirements can differ. Do not overwrite an existing business profile/global branding to decorate one new product; use supported product/session branding. Plugin authorization is not necessarily a server credential. Never extract stored connector credentials. Use the provider's supported sandbox and protected runtime secret channel.

Retrieve current primary integration guidance and inspect the installed SDK's generated types/version before using example parameters. Skill version tables can lag SDK changes. Use the provider's supported flow; avoid rebuilding card collection or a business module through a visual skill.

## Keep purchase state authoritative

Browser quantities, totals and return URLs are inputs, not proof. The server validates product/variant, terms, inventory and price. Persist a durable order before creating a provider session; tie retries to the same selection, original parameters and idempotency key. An ambiguous timeout requires reconciliation, not a fresh charge or automatic release of stock. Respect provider session-expiry limits on later retries.

Confirm payment through signed events and canonical provider records, including environment, account/session identity and financial totals. Handle duplicates, delayed payment, terminal failure, refunds/disputes and stock contention. Paid, fulfilled and reviewed are separate states. A database entitlement or tracking-reference string is not evidence that a licence reached the user, native activation exists or a parcel was dispatched. Operator tools need real authorization; visual dashboard buttons cannot supply it. Preview hosts must not accept live charges.

## Preserve review provenance

Real reviews begin empty until evidence exists. Permit a review only under the product's actual qualification rule (for example, an owned paid/fulfilled order); state that rule visibly. Keep personal account/payment/address fields out of public output. Render customer text safely and moderate with recorded reasons. Relevant critical reviews remain eligible. Never import supplier/Amazon ratings as the site's own, generate testimonials to fill a grid or emit a fictional aggregate rating in schema.

## Report exact acceptance

Keep UI rendering/interaction, local automated service tests, provider sandbox checkout and actual live release as separate evidence. Local signature verification or an HTTP-200 return page does not prove a hosted checkout, payment, webhook delivery, fulfilment or payout. Check mobile selection readability, variant/image consistency, saved choice, actual action destination, empty/error/cancel/pending states and account-owned order access. Publish only the supported state and leave unfinished dependencies explicit. Do not enable policy flags as a substitute for missing facts.

## Origin and maintenance

Derived from the owner-authorized PhoneBridger shop preparation, 6 October 2026: existing merchant account verification differed from charge permission; connector login supplied no Worker key; current SDK hosted parameters differed from older examples; local tests did not exercise provider checkout; genuine shop reviews started empty. This reference is portable guidance, not a fixed currency, provider version, page layout or prohibition on later approved sales. The product-specific activation runbook belongs with its deployment, not in the universal visual skill.
