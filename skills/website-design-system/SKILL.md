# Website Design System

Create an authored website whose pages serve their actual users and share a coherent identity. The portable workflow supplies planning and visual delivery; the active project's builder, business, content, backend and publication contracts still determine the authorized result. It does not impose one palette, layout, section count or commercial stage on every niche.

## 1. Establish the active brief

Read the project's instructions, selected design, relevant implementation, business evidence and actual task. Identify audience, offer, locale, authorized page scope and primary journey. Reuse current research and approved decisions; verify material gaps instead of repeating a full niche investigation for an existing brand's contact page.

For an open identity, inspect current niche and craft references at meaningful desktop/mobile views. Separate market observations, business facts and design hypotheses. Compare nearest existing network designs where the project requires independent identities. Record which decisions the evidence changes; a reference gallery or search snippet is not visual inspection. For planning-only work with unavailable references, mark the direction provisional and record the inspection dependency; do not claim research occurred or expand the authorized task to obtain it.

Preserve an explicitly selected identity and frozen code/product boundaries. Missing facts, unavailable integrations and synthetic data remain explicit. A design request does not establish stock, testimonials, payments, authentication or delivery capability.

## 2. Plan the whole authorized journey

Use [planning records](references/planning-records.md) to create a compact route/page map, global design decisions, section/interaction plan and asset inventory before final asset generation. Existing records may be extended in place. The exact filenames are conventions, not required infrastructure.

Assign each page a user job, next action, content/data source, public/private/prototype mode and needed states. Choose composition and density by page family using [page-family guidance](references/page-families.md). Plan the requested pages and their connections; do not build unrelated dashboards or require a shop for an inquiry-only business.

Sketch the whole homepage's reading sequence and representative inner-page layouts on desktop and mobile. Plan section junctions, recurring navigation, footer and task return paths. Decide which components/assets are shared and which are genuinely page-specific. Specify global token roles and component behavior now; refine section CSS with the actual composition later.

For a new identity compare meaningfully different directions when useful. For an established brand extend its existing system rather than re-running identity selection. Select within delegated authority, or retain the human's selected concept; record the actor accurately without inventing another approval gate.

## 3. Calibrate the system before scaling

Define type hierarchy/line lengths, spacing/grid, palette roles, surface/contrast treatment, icon geometry, image language, light direction and motion policy. Define standard interactive states. Identify a few recognizable treatments grounded in this niche's material or task, plus which pages need quieter presentation. Professional/modern are goals, not instructions to add glass, gradients, dark backgrounds or animation everywhere.

For implementation tasks, implement a representative composition early with real copy and assets. A hero often establishes identity, but choose the best representative unit for the task; an auth form, product chooser or dashboard list may be more informative. Review it in the actual browser before producing every page. Carry accepted decisions into shared tokens/components; do not propagate a failed composition across the site. Planning-only work identifies the calibration unit and its acceptance criteria without performing an unauthorized build.

## 4. Produce sections, assets and states

For image-led compositions apply the available `webpage-section-asset-kit` skill, or read the sibling [source skill](../webpage-section-asset-kit/SKILL.md) in this core distribution. Apply the available ImageGen skill when generating raster concepts/assets. If a required tool is unavailable, report that precise dependency and continue independent work; never claim a generation occurred.

Use the cycle: page/section brief → useful concept → representation and reuse decisions → focused asset production → responsive semantic implementation → actual composition/interaction review. ImageGen helps composition and complex imagery; CSS surfaces, precise SVG icons, exact app UI and live text retain their appropriate representations. Not every section or state needs a generated image.

Maintain stable asset IDs and approved masters across pages. New camera/lighting requirements may justify a versioned edit; a new section alone does not justify regenerating the same product. Match perspective, object scale, contact shadows and light across layers. Reuse source geometry; do not crop low-resolution concept text into production UI. Use the existing media pipeline and keep source/provenance private where required.

Build the full surface recipe and meaningful states: backgrounds, texture, borders, shadows, hover/focus/selection, and applicable loading/empty/error/success states. Inputs, quantities, filters, labels, prices, data and buttons remain editable. Prototype states use explicit isolated fixtures; production success reflects the real backend outcome. Preserve existing APIs rather than hiding absent integrations behind invented success messages.

## 5. Review the page and its neighbours

Follow [acceptance and repair](references/acceptance.md). Inspect the actual section, preceding/following junction and full page at relevant widths. Keep layout variation tied to the reader's question. A quiet gap, divider, color change or continuous background can mark a transition; no compulsory separator between every section.

Review the full set of pages together for brand consistency, task-appropriate density, imagery and icon consistency, meaningful navigation, contrast, responsive reflow and actual interactions. A dashboard can share the brand while using calmer surfaces and denser operational information. Reject noun/palette swaps posing as different niche identities and repeated blocks that add no information.

Repair concrete findings in a bounded batch, then rerun affected checks. Stop when the authorized scope and observable acceptance criteria are met; do not chase invented aesthetic scores, promise first-run perfection or reroll approved art without an observed reason.

## 6. Deliver the authorized result

Apply the [evidence-driven improvement loop](references/improvement-loop.md) throughout the build and before delivery. When the task authorizes system maintenance, fix a small demonstrated shared rule/skill/helper defect autonomously in a coordinated writing window, then verify it. Do not stop at suggesting a routine fix merely because the reader is an agent. Record source, evidence, resulting change and actual adoption status; no artificial change quota or lowering acceptance gates.

Keep research, chosen concepts/selection actor, design decisions, asset inventory, exact prompts and actual review evidence discoverable for the next agent. Use the project's existing records and acceptance tools. Distinguish concept-ready, assets-ready, frontend-implemented, backend-integrated, locally-verified and published; a beautiful page does not prove the adjacent states.

For the paired niche network read [core integration](../webpage-section-asset-kit/references/core-integration.md). Phase-one defaults and explicitly approved later/private work coexist under the actual project contract. This skill creates no new commerce, messaging, account, merge or deployment authorization, and does not replace the site's full builder/audit workflow.
